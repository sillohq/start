# Architecture

Sillo Start is layered so the CLI stays a thin shell over reusable logic. Every
command parses arguments, calls a service layer, and renders the result;
nothing decides anything at the CLI level. That is what lets the whole tool be
driven from tests without a terminal.

```text
cli/            Typer commands — argument handling and rendering only
  ├── create, init, add, package, generate, migrate,
  └── dev, services, build, admin, inspect, doctor

project/        Creating, inspecting and validating projects
packages/       Package-group registry, resolver, installer
blueprints/     Project archetypes
generators/     Component scaffolding
features/       Multi-step feature installers (Inertia)
orchestration/  The supervised process manager behind `dev`
prompts/        The interactive wizard

operations/     Reversible units of work + the transaction that applies them
config/         The manifest: schema, loading, writing
templating.py   Jinja2 rendering
templates/      The .j2 files that become user code
utils/          Console, filesystem, subprocess, env, ports, naming, TOML
plugins/        Entry-point discovery and the registration API
exceptions.py   One error hierarchy the CLI renders uniformly
```

Dependencies point downward. `utils` imports nothing above it; `operations`
uses `utils`; everything else composes operations.

## The manifest is the contract

`sillo.toml` is the only thing that knows what a project is. Commands never
sniff the filesystem to infer configuration — `dev` does not look for a
`frontend/` directory, it reads `[inertia]`.

That has two consequences worth stating. Adding a feature means updating the
manifest, so the manifest is written last in every plan: a failure leaves the
project describing what it actually has. And a project can be reconfigured by
editing the file, which is why writes preserve comments and formatting.

The models are permissive about unknown keys. A project generated by a newer
Sillo Start, or extended by a plugin owning its own section, still loads in an
older tool rather than failing validation.

## Operations and transactions

Every mutation is an `Operation`: a small, named, reversible unit of work with
`describe`, `apply` and `rollback`.

```python
plan = ExecutionPlan("Add auth")
plan.add(
    CreateDirectory("app/services"),
    InstallPythonPackage(["email-validator>=2.0.0"], manager=manager),
    CreateFile("routes/auth.py", source),
    UpdateEnvironment(".env", variables),
    UpdateManifest(lambda m: setattr(m.auth, "enabled", True)),
)
execute_plan(plan, context)
```

Structuring mutation this way buys three things ad-hoc code cannot:

- **A plan that can be shown before anything happens.** `--dry-run` renders the
  same object that would otherwise be applied, so the preview cannot drift from
  the behaviour.
- **Real rollback.** Operations capture the previous bytes, so undoing an edit
  restores the file rather than guessing at an inverse.
- **Uniform safety.** "Never overwrite without `--force`" is implemented once,
  in `CreateFile`, not re-decided at every call site.

Rollback is best-effort by necessity — a subprocess may have had effects we
cannot reverse — so operations that cannot be undone declare themselves
irreversible and the plan says so up front.

## Registries and extension

Package groups, blueprints, generators and services all live in registries
rather than in `if` statements inside commands. `sillo-start package add x`
does not know what `x` is; it asks the registry. That is what makes the plugin
API a few lines rather than a refactor: a plugin registers into the same
registries the built-ins use.

Plugin loading is deliberately fault-tolerant. A plugin that fails to import or
raises during registration is reported and skipped, because one broken
third-party package making `sillo-start` unusable is far worse than running
without it.

## Templates

Templates render against a context built from the manifest, so they ask
`{% if auth.enabled %}` rather than being handed loose booleans. Undefined
variables raise: a template that silently renders an empty string produces a
file that looks fine and fails at import time in someone's project.

The hard constraint is [`docs/verified-apis.md`](verified-apis.md). No template
may import a framework symbol that is not on that page, and every claim there
was verified by importing the real package and introspecting it. Where a
capability genuinely does not exist — a Svelte Vite helper, a framework CLI —
Sillo Start defines an adapter and marks it `TODO(sillo)` rather than inventing
an import that would produce a project that cannot run.

## The orchestrator

`dev` is built from small pieces rather than one loop:

- `ServiceDefinition` — what to run, where, on which port, how to health-check.
- `ServiceRegistry` — the set, ordered so dependencies start first.
- `ManagedProcess` — one child, its reader thread, its restart policy.
- `ProcessSupervisor` — starts, watches, restarts and stops the set.
- `HealthCheck` — whether a service is actually serving, not merely alive.
- `LogMultiplexer` — prefixed, serialised output.

Two details matter more than they look. Children are started in their own
process group, because `uvicorn --reload` and `vite` spawn children of their
own and signalling only the parent leaves those holding ports. And a service
that crashes three times in a minute is not restarted again — restarting
forever would bury the actual error in a scroll of identical tracebacks.

## Testing

Three layers, each catching what the one below cannot:

- **Unit tests** for pure logic: manifest coherence, dependency resolution,
  field parsing, naming.
- **CLI tests** through Typer's runner, asserting on exit codes and output.
- **Integration tests** that generate projects and execute them against the
  real framework in a subprocess.

The third layer is where the value is. Templates can produce perfectly valid
Python that does not work: middleware registered in the wrong order, routers
mounted so one shadows another, models the ORM never discovers. Every
constraint in `verified-apis.md` was found by a failure at this level, and each
now has a test pinning it.
